# Agent-Uplink 설계 스펙

> 상태: 초안 (사용자 검토 대기)
> 작성일: 2026-09-30
> 대상 저장소: https://github.com/pkj8282/Agent-Uplink

---

## 1. 목적과 범위

여러 AI 세션(Claude Code, Claude Desktop 등)이 **하나의 사용자 PC 안에서** 서로 실시간에 가깝게 메시지를 주고받게 하는 시스템.

- 각 AI 세션에 **독립 프로세스**로 붙는 MCP 서버(=Agent Uplink)
- 그 메시지를 중계·보관하는 **커뮤니케이션 서버(Hub)**

두 개의 분리된 산출물을 만든다. 예: 세션 A·B·C·D 각각에 Uplink가 붙고, A가 Hub에 보낸 메시지를 B·C·D가 조회해 확인한다.

### 범위 밖 (이번에 하지 않음)
- 외부 네트워크 노출 / 다른 PC와의 연동 (Hub는 `127.0.0.1` 전용)
- 권한 상승(SYSTEM 등). 이 시스템은 메시지 교환만 하므로 일반 사용자 권한으로 동작한다.
- 인증서/TLS, 계정 시스템, 파일 전송 (필요해지면 별도 작업으로)

### 핵심 기술 제약 (설계의 전제)
MCP(stdio) 서버는 Claude에게 능동적으로 알림을 밀어 넣을(push) 수 없다. 따라서 "B가 A의 메시지를 자동으로 즉시 받는" 것은 불가능하며, **B의 에이전트가 툴(`check`/`wait`)을 호출하는 순간**에만 수신된다. `wait`(롱폴)로 "다음 메시지가 올 때까지 대기"를 제공해 실시간에 근접시킨다.

## 2. 확정된 설계 결정 (사용자 승인 완료)

| 항목 | 결정 |
|------|------|
| Hub 실행 형태 | **자동 스폰**: 첫 MCP가 Hub 없으면 백그라운드로 띄움. 별도 설치 불필요 |
| 기술 스택 | **전부 Node.js/TypeScript** |
| MCP↔Hub 전송 | **로컬 TCP** `127.0.0.1:47800` |
| 메시지 모델 | **브로드캐스트 + 선택적 대상**(`to` 필드) |
| 세션 식별 | `register` 툴로 이름 지정, 생략 시 `uplink-N` 자동 |
| 수신 방식 | **`check`(즉시) + `wait`(롱폴)** 둘 다 |
| 로그 뷰어 | **브라우저 라이브 뷰**(`127.0.0.1:47801`, SSE 실시간) |

## 3. 저장소 · 산출물 구조

단일 npm 워크스페이스로 관리한다(같은 Node/TS 스택 → 한 번의 설치·빌드·타입체크).

```
Agent-Uplink/
├─ hub/              커뮤니케이션 서버 (Node.js TCP, 127.0.0.1)
│  └─ src/
├─ mcp/              Agent Uplink (Node.js stdio MCP 클라이언트)
│  └─ src/           ← ESTS broker.ts의 프레이밍/소켓 패턴 재사용
├─ shared/           공용 타입·프로토콜 정의(요청/응답/메시지 레코드)
├─ package.json      워크스페이스 루트
├─ docs/
└─ README.md
```

로컬 경로: `C:\Research\Agent-Uplink` (GitHub 저장소를 clone).

> `viewer`는 별도 패키지가 아니라 Hub가 직접 서빙하는 HTML 페이지(`hub/src/viewer/`)로 둔다. 뷰어가 Hub 상태에 항상 붙어 있어야 하므로 Hub에 포함하는 편이 단순하다.

## 4. 구성 요소와 책임

### 4.1 Hub (커뮤니케이션 서버)
- `127.0.0.1:47800` TCP 리슨 (에이전트 메시지 채널)
- `127.0.0.1:47801` HTTP 리슨 (브라우저 로그 뷰어 + SSE)
- 세션 등록, 메시지 저장(인메모리 링버퍼 + JSONL append), 브로드캐스트, `wait` 롱폴 대기 관리
- **단일 인스턴스**(5절). 일반 사용자 권한.

### 4.2 MCP (Agent Uplink)
- 각 AI 세션에 stdio로 연결되는 MCP 서버
- 시작 시 Hub에 **연결 시도 → 없으면 자동 spawn**
- Hub로 가는 **영속 TCP 연결 1개**를 세션 생명주기 동안 유지 (실시간 `wait`·접속 감지 근거)
- 에이전트에게 툴 노출(6절)

### 4.3 Viewer (Hub 내장)
- Hub가 서빙하는 최소 HTML + SSE. 사용자가 브라우저로 메시지 흐름을 실시간 확인.
- 자동 스폰 방식의 단점(로그를 보려면 파일/포트를 직접 열어야 함)을 보완하는 사용자 편의 도구.

## 5. 자동 스폰 · 단일 인스턴스 (경합 처리)

여러 세션이 거의 동시에 시작할 때 Hub 중복 실행을 막는다. **포트 바인딩 자체를 뮤텍스로 사용**한다.

1. MCP는 먼저 `47800`에 **연결 시도**. 성공 → 기존 Hub 사용.
2. 실패(`ECONNREFUSED`) → Hub를 **detached(백그라운드)로 spawn** 후, 짧은 백오프로 재연결 시도(예: 100ms 간격 최대 30회).
3. 두 MCP가 동시에 spawn해도, Hub는 부팅 시 포트 바인딩을 시도하고 **`EADDRINUSE`면 조용히 종료**(경쟁에서 진 인스턴스). 승자 하나만 생존.
4. Hub는 부팅 성공 시 `%ProgramData%\AgentUplink\hub.json`에 `{ port, httpPort, pid, startedAt }` 기록. Viewer 안내·디버그용.
5. Hub는 spawn한 MCP보다 오래 생존해야 하므로 **detached + `unref()`**. 모든 세션 연결이 끊기고 **유휴 N분(기본 10분, 설정 가능)** 경과 시 자동 종료. `0`이면 자동 종료 안 함.

### 오염된 포트 방어
`47800`을 Hub가 아닌 다른 프로세스가 점유했을 수 있다. MCP는 연결 직후 **핸드셰이크**(`hello` 요청 → Hub가 매직 문자열 + 프로토콜 버전 응답)를 검증한다. 불일치면 "포트가 다른 프로세스에 점유됨"을 에이전트에 명확히 보고하고 스폰하지 않는다(무한 재시도 금지).

## 6. MCP가 노출하는 툴 (에이전트용)

| 툴 | 인자 | 반환 | 동작 |
|----|------|------|------|
| `register` | `name?: string` | `{ id, name }` | 세션 등록. 이름 생략 시 `uplink-N` 자동. 재호출 시 이름 변경. |
| `send` | `text: string`, `to?: string` | `{ seq }` | 메시지 전송. `to` 지정 시 대상 세션 이름(로그엔 전부 기록), 없으면 전체. |
| `check` | — | `{ messages: Message[] }` | 지난 확인 이후 **나에게 온 새 메시지**(브로드캐스트 + 내 대상)를 즉시 반환. |
| `wait` | `timeoutMs?: number` (기본 30000, 최대 120000) | `{ messages: Message[] }` | 새 메시지가 올 때까지 블록, 오면 즉시 반환. 타임아웃이면 빈 배열(에러 아님). |
| `who` | — | `{ sessions: {name, since}[] }` | 현재 접속 중인 세션 목록. |

- `register`는 다른 툴 사용 전 1회 권장(미등록 상태로 `send` 시 자동 등록 + 자동 이름).
- `check`/`wait`는 **Hub가 세션별로 마지막 전달 seq를 기억**하므로, 에이전트가 커서를 관리할 필요 없다.
- 자기 자신이 보낸 메시지는 기본적으로 `check`/`wait` 결과에서 제외.

## 7. 프로토콜 · 데이터 흐름

### 프레이밍
**4바이트 리틀엔디언 길이 프리픽스 + JSON 본문**. (ESTS의 길이 프리픽스 패턴 재사용, 페이로드만 key:value→JSON으로 교체.)

### 요청/응답
영속 연결 위에서 여러 요청이 오갈 수 있으므로 `id`로 상관한다.

```
요청:  { op: "register"|"send"|"check"|"wait"|"who"|"hello", id: number, ... }
응답:  { ok: boolean, id: number, ...payload | error?: string }
```

`wait`는 응답이 지연될 수 있고, 그 사이 다른 요청의 응답이 먼저 올 수 있다 → `id` 상관이 반드시 필요.

### 메시지 레코드

```ts
interface Message {
  seq: number;      // Hub의 단조 증가 정수
  ts: number;       // epoch ms
  from: string;     // 보낸 세션 이름
  to: string | null; // 대상 세션 이름, 전체면 null
  text: string;
}
```

### 커서/필터
- Hub가 세션별 `lastDeliveredSeq`를 보관.
- `check`/`wait`는 `seq > lastDeliveredSeq` 이면서 (`to == null` 또는 `to == 내 이름`)인 메시지를 반환하고, 반환 후 `lastDeliveredSeq`를 갱신.
- 내가 보낸 메시지(`from == 내 이름`)는 제외.

### 데이터 흐름 (예)
```
A.send("빌드 완료")  → Hub: seq=42 저장, 브로드캐스트, 뷰어 SSE push
B.wait()            → Hub: B의 lastSeq 이후 매칭 있음 → 즉시 [seq42] 반환, B.lastSeq=42
C.check()           → 없으면 [] 즉시, 있으면 매칭 반환
```

## 8. 영속성

- **인메모리 링버퍼(최근 1000개)** = 권위 소스. 조회·필터는 여기서.
- **`%ProgramData%\AgentUplink\messages.jsonl`** append-only 로그 = 내구성·뷰어 히스토리.
- 파일 회전: 10MB 초과 시 `messages.jsonl.1`로 롤(1단계만 보관).
- Hub 재시작 시 JSONL 꼬리에서 최근 메시지 일부(예: 200개)를 링버퍼로 복원(선택적, 뷰어 초기 화면용).
- `seq`는 Hub 생존 동안 단조 증가. 재시작 시 JSONL 마지막 seq+1부터 이어감.

## 9. 로그 뷰어 (브라우저 라이브 뷰)

- Hub가 `127.0.0.1:47801`에서 정적 HTML 1장 + `/events`(SSE) 서빙.
- 페이지 로드 시 최근 메시지(예: 200개)를 렌더 후, SSE로 신규 메시지 실시간 append + 자동 스크롤.
- 표시: `[시각 from→대상] 텍스트`. 대상 없으면 `→ALL`.
- 의존성 없이 순수 HTML/JS 인라인(외부 CDN 불필요, 로컬 전용).
- 접근: 사용자가 브라우저로 `http://127.0.0.1:47801` 열기. README에 안내.

## 10. 에러 처리

- **Hub 연결·spawn 모두 실패**: 원인을 에이전트에 명시(예: node 미설치, 포트 점유). 무한 재시도 금지.
- **포트 오염**(다른 프로세스 점유): 핸드셰이크 불일치로 감지 → 보고, 스폰 중단.
- **소켓 끊김**: 다음 툴 호출 시 자동 재연결 + 동일 이름 재등록. 재연결 실패는 명확히 보고.
- **`wait` 타임아웃**: 정상 동작. 빈 배열 반환(에러 아님).
- **잘못된 인자**(빈 text 등): zod 검증 후 명확한 에러 메시지.

## 11. 테스트 전략

- **Hub 단위**: 등록/커서 갱신/대상 필터/링버퍼 회전/seq 단조성.
- **경합**: 다중 클라이언트 동시 spawn 시 Hub 1개만 생존(포트 뮤텍스 검증).
- **MCP↔Hub 통합**: 가짜 세션 2~3개로 register→send→check/wait 왕복.
- **롱폴**: `wait` 대기 중 다른 세션이 `send` → 즉시 반환되는지, 타임아웃 시 빈 배열인지.
- **재연결**: 소켓 강제 종료 후 다음 툴 호출에서 복구되는지.
- **뷰어**: SSE로 신규 메시지가 실시간 반영되는지(수동 또는 헤드리스 확인).
