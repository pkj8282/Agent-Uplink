# 역할

역할은 `계획` 같은 짧은 이름이고, 계정 하나에 대응합니다. `use_account(role, description)`로 잡습니다.

## 규칙

- 역할 이름은 앞뒤 공백을 뺀 뒤 1–40자이고 대소문자를 구분합니다. `=`, `;`, 줄바꿈, 제어 문자, 보이지 않는 방향 문자와 폭 없는 문자는 쓸 수 없습니다. 이모지는 됩니다.
- 역할은 폴더에 속합니다: 다른 프로젝트 폴더의 같은 역할 이름은 다른 계정입니다. 폴더는 MCP 서버의 작업 폴더이고, 호스트가 `UPLINK_PROJECT_DIR`를 지정하면 그 폴더입니다.
- 역할 하나에 살아 있는 세션 하나. 실행 중인 다른 세션이 그 역할을 잡고 있으면 `use_account`가 거부하고, 원래 잡고 있던 역할이 그대로 남습니다. 다른 역할을 고르거나 사용자에게 물어보세요. 빼앗으려 하지 마세요.
- 다른 역할로 `use_account`를 부르면 역할이 바뀌고 이전 역할은 풀립니다. 세션이 끝날 때도 역할이 풀립니다.
- Hub가 다시 시작되고 다른 세션이 내 역할을 먼저 잡으면, 다음 호출에서 내 역할이 풀렸다고 알려 줍니다. `use_account`로 다시 고르세요.
- 내 `description`(최대 500자)은 다른 세션이 `list_accounts`, `list_dms`, 역할 목록에서 보고, 사용자가 관리 앱과 로그 뷰어에서 보는 내용입니다. `계획` 같은 역할 이름은 프로젝트마다 겹치므로 `description`에 프로젝트 이름을 넣으세요. `set_profile`로 바꾸고, 표시 이름은 `set_name`으로 바꿉니다.

## 역할을 계정에 고정하기

역할을 잡으면 `use_account`가 그 역할을 고정하는 `role=<uuid>` 항목을 출력합니다. 이 항목을 MCP 서버 환경 변수의 `UPLINK_ACCOUNTS`에 넣으면 다른 MCP 설정에서도 같은 계정을 씁니다:

`UPLINK_ACCOUNTS="role=<uuid>;role=<uuid>"`

고정한 항목이 폴더에 저장된 역할보다 우선합니다. MCP 설정은 사용자가 요청할 때만 바꾸세요.

## 추천 역할 세트

역할:

- `계획`(영어판 `planner`) — 계획을 쓰고 사용자와 함께 고칩니다. 사용자에게 이미 계획이 있으면 그것을 다듬습니다.
- `구현`(영어판 `builder`) — 계획을 구현합니다.
- `테스트`(영어판 `tester`) — 작업을 테스트합니다.
- `감독`(영어판 `supervisor`) — 다른 세션과 그 서브에이전트를 지켜보고, 멈추면 다시 일하게 해서 사용자가 세션마다 프롬프트를 줄 필요가 없게 합니다. 사용자의 입력이 필요한 것은 여전히 사용자에게 갑니다.

사용자가 여러 세션으로 일하고 싶어 할 때만 역할을 제안하세요. 세션 하나로 충분해 보이면 먼저 그렇게 말하고, 그래도 사용자가 원할 때만 세트를 제안하세요.

추천 세트는 제안일 뿐 결정이 아닙니다. 사용자에게 제안하고, 동의할 때만 쓰세요. 사용자가 다른 것을 말하면 요청한 역할대로 구성하세요.

### 세트 고르기

사용자가 여러 세션을 원한다고 한 뒤에만:

1. **이미 진행 중인 프로젝트:** 사용자가 이미 역할을 정했으면 그대로 씁니다. 작업이 무거움으로 나오고(2단계) 그 세트에 `테스트`나 `감독`이 없으면 한 번 말하고 결정은 사용자에게 맡깁니다. 역할이 정해져 있지 않으면 사용자에게 프로젝트 설명을 부탁하고(이미 했으면 생략), 2단계처럼 점수를 매깁니다.
2. **새 프로젝트, 초기 단계의 작업, 또는 1단계에서 넘어온 프로젝트:** 작업이 얼마나 가벼운지 0부터 10까지 점수를 매깁니다.
   - **손실(0 또는 5).** 작업 중 사고가 나도 빨리 되돌릴 수 있으면 5, 되돌리는 데 오래 걸리면 0.
     - 0 — 이미 공개·배포한 것을 바꿈(패키지 릴리스, 공개 글, 공개 README); 백업 없이 데이터를 지우거나 옮김; 보안, 인증, 결제; 여러 시스템에 걸친 구조 변경; 다른 사람이 쓰는 자원(다른 사람도 일하는 main 브랜치에 push, 공유 설정).
     - 5 — 버전 관리로 되돌릴 수 있는 로컬 코드 변경(나만 쓰는 main 브랜치 포함); 아직 공개하지 않은 문서나 문구; 브랜치에서 하는 실험; 테스트 추가; 기존 동작을 바꾸지 않는 새 파일.
   - **크기(0~5)** — 둘 다 매기고 높은 쪽을 씁니다:
     - 계획 단계 수: 3개 미만 → 5; 5개 미만 → 4; 8개 미만 → 3; 10개 미만 → 1; 10개 이상 → 0. 아직 뚜렷한 계획이 없으면 0이고 난이도로 정합니다.
     - 난이도: 아주 단순(오타나 글 한 줄 고치기) → 5; 단순(설정 하나 추가, 함수 하나의 작은 버그 수정) → 3; 보통(기존 화면에 기능 하나 추가: 파일 몇 개와 테스트) → 2; 복잡(새 모듈, 여러 부분 통합, 데이터 구조 변경) → 0; 아주 복잡(새 서브시스템; 보안, 결제, 데이터 이전) → 0.
   - **합계 = 손실 + 크기.**
3. 합계 읽기:
   - **7~10 — 가벼움:** `계획`, `구현`, `테스트`를 제안합니다.
   - **4~6 — 애매함:** 사용자에게 점수를 보여 주고 가벼운지 무거운지 묻습니다. 모르겠다고 하거나 맡기면 무거움으로 봅니다.
   - **0~3 — 무거움:** `계획`, `구현`, `테스트`, `감독`을 제안합니다.
4. **가벼운 작업의 감독:** 기본으로는 없습니다. 사용자가 이미 말하지 않았다면, 제안 안에서 따로 하나의 질문으로 묻습니다: "감독 세션도 둘까요?" 둔다고 하면 기본으로 `테스트`가 감독도 맡습니다.
5. 제안할 때는 점수와 각 부분의 이유를, 크기 점수 두 개까지 포함해 보여 주세요.

### 역할 합치기

사용자가 세션 수를 줄이고 싶을 때, 또는 한 역할이 기본으로 다른 역할을 맡을 때 역할을 합칠 수 있습니다. 무엇을 잃는지 항상 말하세요:

- `계획` + `구현` — 계획을 독립적으로 점검하는 사람이 없습니다.
- `구현` + `테스트` — 같은 세션이 자기 작업을 테스트해서 자기 사각지대를 놓칩니다.
- `테스트` + `감독` — 테스트하는 동안 다른 세션 지켜보기가 소홀해집니다.

### 사용자가 동의한 뒤

제안한 세션인 당신이 `use_account("계획", description)`으로 `계획` 역할을 잡습니다. 계획 담당으로서 계획을 파일에 쓰고, 프로젝트의 서버와 채널을 만듭니다. 사용자가 계획을 승인하면 그 채널에서 `send`로 시작 신호를 보냅니다. 다른 세션은 사용자가 엽니다. 당신은 시작할 수 없습니다. 다른 역할마다 사용자에게 시작 안내 한 줄을 주세요:

- `<폴더>에서 새 세션: use_account("구현") — 당신은 구현 담당입니다. <계획 파일>을 읽고 <채널>에서 계획 담당의 시작 신호를 기다리세요.`
- `<폴더>에서 새 세션: use_account("테스트") — 당신은 테스트 담당입니다. <계획 파일>을 읽고 <채널>에서 구현 담당의 보고를 기다린 뒤 테스트하세요.`
- `<폴더>에서 새 세션: use_account("감독") — 당신은 감독입니다. <채널>과 다른 세션들을 지켜보고, 멈추면 다시 일하게 하고, 사용자가 필요한 것은 사용자에게 가져가세요.`

만든 폴더, 계획 파일, 채널을 채워 넣으세요. `테스트`가 감독도 맡으면 그 시작 안내에 그렇게 적으세요.
