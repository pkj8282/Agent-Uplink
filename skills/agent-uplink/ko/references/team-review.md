# 팀 리뷰 루프

계획, 구현, 테스트를 따로 맡은 세션들이 일하는 프로젝트용입니다.

## 준비

- 프로젝트마다 서버 하나, 단계마다 채널 하나(예: `m5-sync`, 다음은 `m6-sync`). 단계가 끝나면 새 채널을 열어 채널마다 짧게 유지합니다.
- `lobby`에 프로젝트의 서버와 채널을 적은 한 줄을 올려서, 다른 일을 하는 세션이 무시할 수 있게 합니다.
- 각 세션은 메시지 하나로 들어옵니다: 역할, 할 일, 하지 않을 일(예: "테스트 담당은 코드를 고치지 않는다").

## 루프

프로젝트가 커밋을 쓰면 아래 형식으로 보고하고, 아니면 해시 대신 바뀐 파일을 적습니다.

1. **구현:** 커밋할 때마다 한 줄 — `Task <N> commit <hash> — <what changed>, <tests: passed/total>`. 계획과 달라진 점은 "ruling — please judge"(판단 요청)로 표시합니다.
2. **테스트 / 리뷰:** 커밋을 계획과 스펙에 비춰 확인합니다. 테스트는 그 커밋의 스냅샷에서 돌리고, 구현 담당의 작업 트리에서는 절대 돌리지 않습니다. 판정과 지적으로 답합니다:
   - 판정: 승인 / 수정 후 승인 / 차단;
   - 지적마다 **Critical**, **Important**, **Minor** 등급, 재현 방법, 고칠 방안;
   - 끝에 열린 요청 목록.
3. **구현:** 별도 커밋으로 고치고(다음 작업에 섞지 않음) 하나씩 보고합니다: `fix <finding> — <hash>, <test that now fails without the fix>`.
4. **테스트 / 리뷰:** 다시 확인하고 지적마다 종결을 표시합니다.

## 규칙

- 사용자에게 속한 결정 — 범위, 제품 규칙, 스펙 변경 — 은 사용자에게 갑니다. 세션끼리 정하지 말고 질문과 선택지를 보고하세요.
- 보고한 뒤에도 일하는 세션은 턴을 끝내지 않습니다: 다음 요청이나 "계속"이 닿을 수 있게 `wait` 반복 안에 머뭅니다. (Claude Code에서는 대신 `/loop`로 주기적으로 확인할 수 있습니다.)
- 계획 담당이나 감독의 "승인된 계획대로 계속"은 따라도 됩니다. 계획 밖의 일과 모든 부수 효과(삭제, push, 공개, PC 밖으로 보내기)는 사용자 확인이 필요합니다.

## 질문과 답

- **묻기:** 그 자체로 이해되는 메시지 하나 — 배경, 정확한 질문, 보이는 선택지, 그동안 할 일. 그다음 `wait`(기다리는 한도는 메시지 문서 참고).
- **답하기:** 같은 채널에 답합니다. 어느 질문에 답하는지부터 적습니다. 답할 수 없으면 그렇다고 말하고 누가 답할 수 있는지 알려 줍니다.
- **작업 받기:** 보낸 쪽이 도착을 알 수 있게 "received — starting <task>"(받음 — <작업> 시작)로 답하고, 끝나면 보고합니다.
